# DESIGN-015

## Overview

사람이 입력한 테스트 실행 로그를 받아 원인 후보, 각 원인 후보의 근거, 다음 확인 사항을 돌려주는 독립 Python/FastAPI 서비스(`services/log-analyzer/`)의 1단계 설계다. 근거: TASK-015, ADR-007.

이 단계의 분석기는 결정적으로 동작하는 가짜 분석기뿐이다. 설계의 목표는 다음을 확정하는 것이다.

* API 계약 (요청, 성공 응답, 오류 응답)
* 입력 검증과 크기 제한
* 분석기가 돌려준 근거를 입력 로그로 검증하는 규칙
* 분석기 오류와 타임아웃의 처리
* 테스트 방식과 실행 환경

2단계에서는 이 계약을 유지한 채 분석기 구현만 실제 AI 모델로 교체한다. 실제 AI 연결, Spring 연동, 배포, 워크플로, 저장, 인증은 범위 밖이다.

## Architecture Overview

`architecture.md`의 Log Analysis Service 절을 따른다. Spring 애플리케이션과 코드, 빌드, 실행 단위를 공유하지 않으며 상태를 저장하지 않는다.

```
HTTP 요청
   │
   ▼
[API 계층]            요청 스키마 검증, 오류 응답 변환
   │
   ▼
[분석 서비스]          타임아웃 적용, 분석기 호출, 근거 검증, 응답 조립
   │            │
   ▼            ▼
[분석기 경계]      [근거 검증기]
   ▲
   │ (1단계 구현)
[가짜 분석기]
```

| 구성 요소 | 책임 |
| --------- | ---- |
| API 계층 | 요청 본문을 스키마로 검증하고, 분석 서비스를 호출하고, 결과와 오류를 HTTP 응답으로 바꾼다. 분석 로직을 갖지 않는다. |
| 분석 서비스 | 분석기 호출에 타임아웃을 적용하고, 분석기 결과의 근거를 검증하고, 검증되지 않은 근거를 제외해 성공 응답을 조립한다. HTTP를 알지 않는다. |
| 분석기 경계 | 로그 텍스트를 받아 검증 전 분석 결과를 비동기로 돌려주는 교체 가능한 경계. 실패는 분석기 오류로 알린다. |
| 가짜 분석기 | 분석기 경계의 1단계 구현. 정상 결과, 분석기 오류, 타임아웃(응답하지 않음)을 설정에 따라 결정적으로 재현한다. |
| 근거 검증기 | 근거가 입력 로그의 해당 줄에 실제로 있는지 판단하는 순수 함수. |
| 오류 처리 | 서비스 전역에서 입력 오류, 분석기 오류, 타임아웃, 예상하지 못한 오류를 공통 오류 응답 형식으로 바꾼다. |
| 설정 | 타임아웃 값을 환경 변수에서 읽는다. 테스트에서는 앱을 만들 때 직접 주입한다. |

앱은 분석기와 설정을 인자로 받아 만드는 팩토리로 생성한다. 테스트는 이 팩토리로 가짜 분석기의 동작과 짧은 타임아웃을 주입한다. 로컬 실행용 앱은 기본 가짜 분석기와 환경 변수 설정으로 만든다.

## API Design

### POST /analyses

테스트 실행 로그를 분석한다. 요청과 결과는 저장하지 않으므로 성공 상태 코드는 201이 아닌 200이다.

Request (`Content-Type: application/json`):

```json
{
  "log": "============================= test session starts ==============================\ncollected 3 items\n\ntests/test_order.py::test_total FAILED\nE   AssertionError: assert 90 == 100\n..."
}
```

Response 200:

```json
{
  "causes": [
    {
      "summary": "주문 합계 계산 결과가 기대값과 다르다",
      "evidence": [
        { "line": 4, "text": "tests/test_order.py::test_total FAILED" },
        { "line": 5, "text": "E   AssertionError: assert 90 == 100" }
      ]
    }
  ],
  "next_checks": [
    "합계 계산에 할인이 두 번 적용되는지 확인한다"
  ],
  "excluded_evidence_count": 0
}
```

* `causes`가 빈 배열일 수 있다. 분석기가 원인 후보를 찾지 못했거나, 모든 원인 후보의 근거가 검증되지 않아 제외된 경우다. 이때도 200이다.
* `excluded_evidence_count`는 검증되지 않아 제외한 근거의 수다.

Error (모든 오류 응답은 같은 형식이다):

```json
{
  "error": {
    "code": "ANALYZER_TIMEOUT",
    "message": "분석이 제한 시간 안에 끝나지 않았습니다."
  }
}
```

* 413 `LOG_TOO_LARGE`: `log`가 100,000자를 넘는다. 분석기를 호출하지 않는다.
* 422 `INVALID_INPUT`: 본문이 JSON 객체가 아니거나, `log`가 없거나, 문자열이 아니거나, 공백만 있거나 비어 있다. 분석기를 호출하지 않는다. `message`는 어떤 조건을 어겼는지 알려 준다.
* 500 `INTERNAL_ERROR`: 예상하지 못한 내부 오류. 메시지는 고정 문구이며 내부 정보를 담지 않는다.
* 502 `ANALYZER_ERROR`: 분석기가 오류를 알렸다.
* 504 `ANALYZER_TIMEOUT`: 분석기가 타임아웃 안에 결과를 돌려주지 않았다.

Timeout: 분석기 호출 1회에 기본 10초. 환경 변수 `LOG_ANALYZER_TIMEOUT_SECONDS`(0보다 큰 실수)로 바꿀 수 있고, 테스트는 앱 팩토리로 짧은 값을 주입한다. 입력 검증과 근거 검증은 타임아웃에 포함하지 않는다.

오류 응답의 `message`에는 스택 트레이스, 내부 경로, 예외 클래스 이름, 입력 로그 원문을 넣지 않는다.

## Data Model

### Model: AnalysisRequest

| Field | Type   | Constraints | Description |
| ----- | ------ | ----------- | ----------- |
| log   | string | 필수. 앞뒤 공백을 뺀 길이 1자 이상. 원문 길이 100,000자 이하(초과 시 413) | 사람이 입력한 테스트 실행 로그 원문 |

Persistence: 없음

### Model: Evidence

| Field | Type    | Constraints | Description |
| ----- | ------- | ----------- | ----------- |
| line  | integer | 1 이상, 입력 로그의 줄 수 이하 | 근거가 있는 줄 번호 (1부터) |
| text  | string  | 앞뒤 공백을 뺀 길이 1자 이상. 성공 응답에서는 검증에 쓴 값(앞뒤 공백을 뺀 값) | 해당 줄에 실제로 있는 문자열 |

Persistence: 없음

### Model: Cause

| Field    | Type           | Constraints | Description |
| -------- | -------------- | ----------- | ----------- |
| summary  | string         | 1자 이상 | 원인 후보 설명 |
| evidence | list[Evidence] | 성공 응답에서는 1개 이상, 모두 검증됨 | 원인 후보의 근거 |

Persistence: 없음

### Model: AnalysisResponse

| Field                   | Type        | Constraints | Description |
| ----------------------- | ----------- | ----------- | ----------- |
| causes                  | list[Cause] | 0개 이상 | 검증된 근거를 가진 원인 후보 |
| next_checks             | list[string]| 0개 이상 | 다음 확인 사항 |
| excluded_evidence_count | integer     | 0 이상 | 검증되지 않아 제외한 근거의 수 |

Persistence: 없음

### Model: AnalyzerResult (내부 값, 검증 전)

| Field       | Type        | Constraints | Description |
| ----------- | ----------- | ----------- | ----------- |
| causes      | list[Cause] | evidence가 비어 있거나 검증되지 않았을 수 있음 | 분석기가 돌려준 원인 후보 |
| next_checks | list[string]| 0개 이상 | 분석기가 돌려준 다음 확인 사항 |

Persistence: 없음

### Model: ErrorResponse

| Field         | Type   | Constraints | Description |
| ------------- | ------ | ----------- | ----------- |
| error.code    | string | `INVALID_INPUT`, `LOG_TOO_LARGE`, `ANALYZER_ERROR`, `ANALYZER_TIMEOUT`, `INTERNAL_ERROR` 중 하나 | 오류 종류 |
| error.message | string | 1자 이상, 내부 정보 없음 | 사람이 읽을 설명 |

Persistence: 없음

### 근거 검증 규칙

* 입력 로그를 줄 단위로 나눈다. 줄 구분자는 `\n`이며, 줄 끝의 `\r`은 제거하고 비교한다. 줄 번호는 1부터 센다.
* 근거는 다음을 모두 만족할 때만 검증된 것으로 본다.
  1. `line`이 1 이상, 줄 수 이하다.
  2. `text`의 앞뒤 공백을 뺀 값(이하 정규화 값)이 비어 있지 않다.
  3. 정규화 값이 해당 줄에 그대로(대소문자 구분, 부분 문자열) 들어 있다. 문자열 안쪽의 공백은 바꾸지 않으므로, 줄의 연속 공백과 근거의 공백 수가 다르면 검증되지 않는다.
* 성공 응답의 `text`에는 분석기가 준 원문이 아니라 검증에 쓴 정규화 값을 넣는다. 응답에 나가는 문자열은 항상 검증된 문자열과 같다.
* 검증되지 않은 근거는 응답에서 제외하고 `excluded_evidence_count`에 센다.
* 검증된 근거가 하나도 남지 않은 원인 후보는 응답에서 제외한다. 원인 후보가 제외될 때 그 근거는 이미 개별적으로 세어져 있으므로 따로 세지 않는다.
* `next_checks`는 로그 근거가 아니므로 검증하지 않고, 앞뒤 공백을 뺀 값이 비어 있는 항목만 제외한다.

```

 ├── uv.lock                 # uv가 생성
 ├── src/
 │   └── log_analyzer/
 │       ├── __init__.py
 │       ├── app.py          # 앱 팩토리, 로컬 실행용 앱
 │       ├── api.py          # POST /analyses 라우팅
 │       ├── schemas.py      # 요청·응답·오류 모델
 │       ├── service.py      # 분석 서비스 (타임아웃, 근거 검증 적용, 응답 조립)
 │       ├── evidence.py     # 근거 검증기
 │       ├── analyzer.py     # 분석기 경계, 분석기 오류
 │       ├── fake_analyzer.py# 가짜 분석기
 │       ├── errors.py       # 전역 오류 처리
 │       └── config.py       # 설정 (타임아웃)
 └── tests/
     ├── conftest.py
     ├── test_api.py
     ├── test_service.py
     ├── test_evidence.py
     ├── test_fake_analyzer.py
     └── fixtures/
         └── logs/           # 직접 만든 테스트 로그 (*.log)
```

* `src/` 레이아웃을 쓴다. 테스트가 설치된 패키지를 import하게 되어, 경로 설정에 기대는 테스트를 막는다.
* `uv sync`가 `log_analyzer`를 설치된 패키지(편집 가능 설치)로 넣도록 `pyproject.toml`에 빌드 시스템을 둔다.
  * `[build-system]`: 빌드 백엔드 hatchling (`requires = ["hatchling"]`, `build-backend = "hatchling.build"`)
  * `[tool.hatch.build.targets.wheel]`: `packages = ["src/log_analyzer"]`
  * pytest 설정에 `pythonpath`를 두지 않는다. import는 설치로만 해결한다.
* 이 밖의 파일(README, `.python-version`, CI 설정 등)은 만들지 않는다. Python 버전은 `pyproject.toml`의 `requires-python`으로 고정한다.

## Key Design Decisions

* 성공 상태 코드는 200이다: 요청과 결과를 저장하지 않으므로 생성된 자원이 없다.
* 검증되지 않은 근거는 제외하고 그 수를 응답에 남긴다: Trade-offs 참조.
* 원인 후보가 없으면 빈 배열로 200을 돌려준다: "원인을 찾지 못함"은 서비스 오류가 아니라 정상적인 분석 결과다.
* 입력 크기 제한은 100,000자다: 일반적인 단일 테스트 실행 로그를 담으면서 2단계에서 AI 모델에 보낼 입력 크기를 미리 제한한다. 초과는 형식 오류와 구분해 413으로 알린다. 100,000자와 타임아웃 기본 10초는 초기 개발용 값이며, 실제 AI 연동 단계에서 모델의 입력 한도와 응답 시간을 보고 재평가한다.
* 형식 오류는 422로 통일한다: FastAPI의 기본 검증 상태 코드와 같아 계약이 자연스럽다. 다만 응답 본문은 기본 형식 대신 공통 오류 형식으로 바꾼다.
* 분석기 오류는 502, 타임아웃은 504다: 서비스 자체가 아니라 하위 의존(분석기)의 실패임을 HTTP 의미에 맞게 구분한다. 1단계의 가짜 분석기에도 같은 계약을 적용해 2단계에서 바꿀 것이 없게 한다.
* 타임아웃은 분석 서비스가 분석기 호출 전체에 건다: 분석기마다 다른 타임아웃 동작에 서비스 계약(504)을 맡기지 않는다. 타임아웃이 나면 분석기 호출을 취소한다.
  * 한계: 이 방식은 분석기가 취소에 협조하는 비동기 구현이라는 전제에 선다. 분석기가 이벤트 루프를 막는 동기 작업(블로킹 I/O, CPU 작업)을 하면 타임아웃이 제때 동작하지 않고, 취소 후 정리도 분석기 구현에 달려 있다. 1단계의 가짜 분석기는 비동기 대기만 하므로 이 전제를 만족한다.
  * 2단계(실제 AI 연동)에서는 HTTP 클라이언트 자체의 타임아웃 설정과, 서비스 타임아웃으로 취소될 때 요청이 실제로 중단되고 자원이 정리되는지를 별도로 설계하고 검증한다.
* 분석기 경계는 비동기다: 2단계의 실제 AI 호출은 네트워크 대기가 대부분이고, 비동기 경계여야 타임아웃 취소가 자연스럽다.
* 가짜 분석기는 동작을 설정으로 고른다. 정상 결과(지정한 결과 그대로 반환), 오류(분석기 오류 발생), 응답 없음(취소될 때까지 대기) 세 가지다. 로컬 실행용 기본 동작은 정상 결과이며, 입력 로그에서 `FAILED`, `ERROR`, `Error`, `Exception`이 들어간 처음 3줄을 근거로 하는 원인 후보 1개를 만든다. 결정적이고, 실제 AI처럼 보이게 꾸미지 않는다.
* 설정은 환경 변수 하나(`LOG_ANALYZER_TIMEOUT_SECONDS`)만 둔다: 1단계에 secret이나 외부 주소가 없다. 값이 숫자가 아니거나 0 이하이면 앱 시작 시 실패한다.
* 로그에는 요청 크기, 결과 코드, 처리 시간만 남기고 입력 로그 원문은 남기지 않는다: 테스트 로그에 민감한 값이 섞일 수 있다.

## Trade-offs

### 입력 로그에서 검증되지 않은 근거 처리

| Option | Pros | Cons | Selected |
| ------ | ---- | ---- | -------- |
| A. 해당 근거를 제외하고 응답 (제외 수를 응답에 포함) | 검증된 결과는 사용자에게 전달된다. 2단계 실제 AI가 일부 근거를 조금 다르게 인용해도 전체 요청이 실패하지 않는다. `excluded_evidence_count`로 제외 사실이 드러난다. | 사용자가 제외 사실을 놓칠 수 있다. 원인 후보가 통째로 빠질 수 있다. | ✅ |
| B. 요청 전체를 실패 처리 (예: 502) | 계약이 가장 엄격하고 단순하다. 분석기 품질 문제가 즉시 드러난다. | 근거 하나가 틀려도 검증된 결과까지 모두 버린다. 실제 AI에서는 실패가 잦아져 서비스 가치가 떨어진다. 같은 로그로 재시도해도 결과가 같을 수 있다. | |
| C. 검증 여부를 표시해 모두 응답 | 정보 손실이 없다. | TASK-015의 "검증되지 않은 근거는 성공 응답에 포함하지 않는다"를 어긴다. | |

선택 이유: TASK-015는 검증되지 않은 근거를 성공 응답에 넣지 않는 것만 요구하며, 사용자에게 필요한 것은 근거가 확인된 원인 후보다. A는 이 요구를 지키면서 검증된 결과를 살리고, 제외한 수를 응답에 남겨 조용한 손실을 막는다. B는 2단계에서 일부 인용 오차만으로 전체 요청이 실패하게 된다. 분석기 품질은 제외 수와 서비스 로그로 관찰한다.

### 입력 크기 초과의 상태 코드

| Option | Pros | Cons | Selected |
| ------ | ---- | ---- | -------- |
| A. 413 `LOG_TOO_LARGE` | 형식 오류와 크기 초과를 상태 코드만으로 구분할 수 있다. HTTP 의미와 맞는다. | 오류 처리에서 크기 검사를 형식 검증과 따로 다뤄야 한다. | ✅ |
| B. 422 `INVALID_INPUT`에 포함 | 오류 경로가 하나다. | 사용자가 로그를 줄여야 하는지 고쳐야 하는지 코드로 구분할 수 없다. | |

선택 이유: 크기 초과는 입력을 줄이면 해결되는 별도 상황이며, 2단계에서 AI 입력 한도와 연결된다. 상태 코드로 구분하는 편이 사용자와 테스트 모두에 명확하다.

### 타임아웃 적용 위치

| Option | Pros | Cons | Selected |
| ------ | ---- | ---- | -------- |
| A. 분석 서비스가 분석기 호출 전체를 감싼다 | 취소에 협조하는 비동기 분석기라면 구현과 관계없이 같은 시간 제한이 적용된다. 가짜 분석기의 응답 없음 동작으로 결정적으로 재현된다. | 분석기가 이벤트 루프를 막으면 동작하지 않는다. 분석기 내부의 정리 작업은 취소 처리에 맡겨야 한다. | ✅ |
| B. 각 분석기 구현이 스스로 타임아웃을 지킨다 | 2단계에서 HTTP 클라이언트의 타임아웃을 그대로 쓸 수 있다. | 구현마다 동작이 달라지고, 가짜 분석기로 서비스 수준 타임아웃을 검증할 수 없다. | |

선택 이유: 타임아웃은 서비스 계약(504)이므로 서비스가 보장해야 한다. 2단계에서 HTTP 클라이언트 타임아웃을 추가하더라도 서비스 수준 타임아웃은 그대로 둔다.

## Non-Functional Design

* 성능: 분석기 호출 1회에 기본 10초 제한. 입력은 100,000자 이하. 근거 검증은 로그 줄 수에 비례하며 별도 최적화는 하지 않는다. 요청 본문 전체 크기 제한은 이 단계에서 두지 않는다(배포 범위 밖이며, 100,000자 검사는 JSON 파싱 후에 한다).
* 보안: secret과 외부 호출이 없다. 오류 응답과 서비스 로그에 입력 로그 원문, 스택 트레이스, 내부 경로를 남기지 않는다. 인증은 범위 밖이다.
* 외부 배포 전 검토 사항: 이 단계에는 요청 본문 전체 크기 제한과 인증이 없다. 로컬 개발 전용이며, 외부에 배포하기 전에 두 가지를 별도로 검토한다.
* 확장성: 2단계에서 분석기 경계의 구현만 추가하고, API 계약, 근거 검증, 오류 처리, 타임아웃은 바꾸지 않는다.
* 테스트 실행 시간: 자동화 테스트 전체가 10초 안에 끝난다. 타임아웃 테스트는 0.1초 이하의 타임아웃을 주입한다.

### 테스트 방식

* 도구: pytest. API 테스트는 FastAPI의 로컬 테스트 클라이언트를 쓴다. 비동기 함수의 단위 테스트는 표준 라이브러리의 이벤트 루프 실행으로 호출해 추가 pytest 플러그인을 두지 않는다.
* 자동화 테스트는 네트워크, 실제 AI, secret, 환경 변수 설정 없이 통과한다. 타임아웃 값은 앱 팩토리로 주입한다.
* 실제 AI를 호출하는 테스트는 이 단계에 없다. 2단계에서 별도 마커로 구분하고 기본 실행에서 제외한다.

| 파일 | 대상 | 검증 |
| ---- | ---- | ---- |
| `test_evidence.py` | 근거 검증기 (단위) | 줄 번호 범위 밖, 빈 텍스트, 공백만 있는 텍스트, 다른 줄의 문자열, 부분 문자열 일치, 앞뒤 공백이 섞인 부분 문자열(검증되고 결과 값은 공백을 뺀 값), 안쪽 공백 수가 다른 문자열(검증 실패), CRLF 로그, 대소문자 구분 |
| `test_fake_analyzer.py` | 가짜 분석기 (단위) | 정상 결과 반환, 오류 발생, 응답 없음 동작이 취소로 끝남, 기본 동작이 로그의 줄을 근거로 쓰는지 |
| `test_service.py` | 분석 서비스 (단위) | 검증되지 않은 근거 제외와 제외 수, 근거가 모두 제외된 원인 후보 제거, 빈 `next_checks` 항목 제거, 분석기 오류와 타임아웃이 각각 구분된 예외로 전달 |
| `test_api.py` | API (테스트 클라이언트) | 아래 표 |

`test_api.py`의 경우와 assertion:

| 경우 | 상태 코드 | 본문 검증 | 분석기 호출 |
| ---- | --------- | --------- | ----------- |
| fixture 실패 로그, 정상 결과 | 200 | `causes`, `next_checks`, `excluded_evidence_count`의 값과 모든 근거가 로그의 해당 줄에 있음 | 1회 |
| 앞뒤 공백이 섞인 부분 문자열 근거 (예: 줄 `E   AssertionError: assert 90 == 100`에 대해 `"  assert 90 == 100 "`) | 200 | 응답 `text`가 `"assert 90 == 100"`이고 그 값이 해당 줄에 있음, `excluded_evidence_count == 0` | 1회 |
| 로그에 없는 근거가 섞인 결과 | 200 | 그 근거가 없고 `excluded_evidence_count`가 기대값 | 1회 |
| 근거가 모두 검증되지 않은 결과 | 200 | `causes`가 빈 배열 | 1회 |
| `log` 없음 | 422 | `error.code == "INVALID_INPUT"` | 0회 |

### 실행 환경

* Python 3.12 (`requires-python = ">=3.12,<3.13"`), uv로 가상 환경과 의존성을 관리한다.
* 의존성: 실행용 FastAPI, uvicorn. 개발용 pytest, httpx(테스트 클라이언트). Pydantic v2는 FastAPI를 통해 들어오며 버전 범위를 명시한다. 정확한 버전은 `uv.lock`으로 고정한다.
* 명령은 `services/log-analyzer/`에서 실행한다.
  * 의존성 설치: `uv sync`
  * 문법 검사: `uv run python -m compileall -q src tests`
  * 자동화 테스트: `uv run pytest`
  * 설치된 패키지 import 확인: `uv run python -c "import log_analyzer; print(log_analyzer.__file__)"`. `src/` 경로를 `sys.path`에 넣지 않은 상태에서 성공하고, 출력 경로가 `services/log-analyzer/src/log_analyzer/__init__.py`여야 한다.
  * 로컬 기동(수동 확인용): `uv run uvicorn log_analyzer.app:app`
* import·기동 검증 범위: 자동화 검증은 문법 검사, 설치된 패키지 import 확인, 자동화 테스트다. API 테스트가 앱 팩토리로 앱을 만들고 요청하므로 앱 모듈의 import와 앱 생성은 여기서 확인된다. uvicorn 기동은 자동화하지 않고 구현 보고에 수동 확인 결과를 적는다.
* 소유자 Mac에서 Python 3.12와 uv 설치는 아직 확인되지 않았다(ADR-007 8. Notes). 구현 착수 전에 확인한다.

## Implementation Guide

1. `services/log-analyzer/pyproject.toml`을 만든다. 패키지 이름 `log-analyzer`, `requires-python`, 실행·개발 의존성, Package Structure에 적은 빌드 시스템(hatchling, `src/log_analyzer` 패키지 지정), pytest 설정(`testpaths = ["tests"]`, `pythonpath` 없음)을 정의하고 `uv lock`으로 `uv.lock`을 만든다. `uv sync` 후 설치된 패키지 import 확인 명령이 통과하는지 먼저 확인한다.
2. `schemas.py`에 Data Model의 모델을 정의한다. `log`의 필수·타입·공백 검사는 스키마에서 한다. 100,000자 검사는 413과 구분하기 위해 스키마에 넣지 않고, API 계층이 분석 서비스를 호출하기 전에 입력 검증으로 한다.
3. `evidence.py`에 근거 검증 규칙을 구현하고 `test_evidence.py`를 먼저 통과시킨다. 검증 결과는 검증 여부와 정규화 값을 함께 돌려주어, 응답 조립이 정규화 값을 쓰게 한다.
4. `analyzer.py`에 분석기 경계와 분석기 오류를, `fake_analyzer.py`에 세 가지 동작과 호출 횟수 기록을 구현하고 `test_fake_analyzer.py`를 통과시킨다.
5. `service.py`에 타임아웃 적용, 분석기 오류·타임아웃의 구분, 근거 검증과 제외 수 집계를 구현하고 `test_service.py`를 통과시킨다.
6. `config.py`에 타임아웃 설정을, `errors.py`에 공통 오류 응답 변환(FastAPI 기본 검증 오류 포함)을 구현한다.
7. `api.py`와 `app.py`를 만든다. 앱 팩토리는 분석기와 설정을 받는다. 로컬 실행용 앱은 기본 가짜 분석기와 환경 변수 설정을 쓴다.
8. `tests/fixtures/logs/`에 테스트 로그를 직접 만들고 `test_api.py`의 표를 모두 구현한다.
9. 문법 검사, 설치된 패키지 import 확인, `uv run pytest`가 통과하는지 확인하고, uvicorn 수동 기동 결과를 구현 보고에 적는다.

주의사항

* `services/log-analyzer/` 밖의 파일은 TASK-015 상태 변경 외에 바꾸지 않는다.
* API 계층에 근거 검증이나 타임아웃 로직을 두지 않는다.
* 예외를 삼키지 않는다. 예상하지 못한 예외는 서비스 로그에 남기고 500 공통 형식으로 응답한다.
* 실제 AI SDK나 HTTP 클라이언트를 실행 의존성에 추가하지 않는다.
